<ProblemBox>
- 「WebアプリなんだからPlaywrightやSeleniumで簡単に自動化できるはず」と無茶振りされて困っている
- Shadow DOMや動的セレクタへの対処だけでは、テストの崩壊とFlaky（不安定）化が止まらない

「Salesforceの画面テスト、PlaywrightかSeleniumでサクッと自動化しといて！」

もしプロジェクトでこう言われたら、QAエンジニアやテスト自動化担当者は全力で警戒すべきです。WebアプリケーションのE2E（End-to-End）テスト自動化が当たり前になった現代においても、**Salesforce（Lightning Experience）のUIテスト自動化は、Web開発の中で最も難易度が高く、挫折率が高い領域**の一つだからです。

ネット上ではよく「Shadow DOMがあるから」「IDが動的だから」といった表面的な理由が語られます。しかし、それらは**結果として現れている現象に過ぎません**。

この記事では、なぜSalesforceのテスト自動化が構造的にこれほど難しいのか、**アーキテクチャレベルの根本原因**と、それでも現場で自動化を成功させるための現実的なアプローチを解説します。

---

## 根本原因①：「メタデータ駆動UI」ゆえにDOMを所有できない

通常のWebアプリケーション（ReactやVueなどで構築された自社開発システム）では、開発者がHTMLやJSXを直接記述します。そのため、テスト自動化をやりやすくするために `data-testid="submit-button"` のような安定した属性を付与する権利（DOMの所有権）を持っています。

しかし、Salesforceは根本的に設計が異なります。Salesforceは**「メタデータ駆動型マルチテナントアーキテクチャ」**です。

画面のHTMLは開発者が書いているのではなく、**「オブジェクト定義・ページレイアウト・Lightningページ・プロファイル権限」などのメタデータを、Salesforceのランタイムが動的に解釈してブラウザ上で生成（レンダリング）**しています。

- **テスト用属性（`data-testid`等）を標準画面に付与できない**
- **設定変更（項目の追加やレイアウト変更）一つで、DOMの階層構造ごと別物に変わる**
- **同じURL・同じコンポーネントでも、ログインユーザーの権限やレコードタイプによって描画されるDOMが全く異なる**

つまり、テスト自動化エンジニアが相手にするDOMは**「自社でコントロールできないブラックボックスの生成物」**であり、これが通常のWebアプリと同じ感覚でセレクタを書くと即死する最大の理由です。

---

## 根本原因②：Aura・LWC・Visualforceが同居する「ハイブリッドSPA」の罠

Salesforceの画面（Lightning Experience）は、単一の最新フレームワークで作られているわけではありません。歴史的経緯により、**3つの異なる技術世代が同一画面上に混在する巨大なハイブリッドSPA**として動作しています。

1. **LWC（Lightning Web Components）**: Web Components標準ベースの最新UI
2. **Auraフレームワーク**: LWC以前の独自コンポーネント基盤（標準画面の根幹に多数残存）
3. **Visualforce / AppExchange**: `iframe` として埋め込まれるレガシー画面や外部アプリ

この混在環境が、テスト自動化において致命的な複雑さを生みます。

### 1. Synthetic ShadowとLWS（Lightning Web Security）の隔離
LWCはスタイルとDOMをカプセル化する**Shadow DOM**を使用しますが、さらにブラウザ互換性やセキュリティ隔離（LWS / Locker Service）のためにSalesforce独自の**Synthetic Shadow（合成Shadow DOM）**が介在します。これにより、標準的なXPathや従来のSeleniumのDOM走査ロジックが境界を越えられず、要素を見失います。

### 2. ポータル描画と遅延レンダリング
ドロップダウン（Combobox）、モーダル、検索ルックアップなどのUI要素は、クリックされるまでDOMツリーに存在しません。さらに開いた瞬間、元のコンポーネント内ではなく**`<body>`直下や別のShadow Root内にポータル（Portal）として動的挿入**されます。そのため「親要素から辿って子要素をクリックする」という構造的なロケーターが通用しません。

### 3. LDS（Lightning Data Service）によるクライアントキャッシュ
SPAである以上、画面遷移してもページのリロードは走りません。裏側ではAuraのライフサイクルや**LDS（Lightning Data Service）の強力なクライアントキャッシュ**が生き続けています。
「テストコード上ではデータを更新して保存したはずなのに、次の画面遷移でキャッシュされた古い値が表示されてアサーションが落ちる」「テストの実行順序を変えるとキャッシュの影響で落ちる」といった**極悪なFlaky（不安定）テスト**が頻発します。

## 根本原因③：テスト環境（Sandbox）の物理的・構造的制約

モダンなWeb開発のテスト自動化では、「テスト実行ごとにDockerコンテナでDBを立ち上げ、マイグレーションとシードデータ投入を行い、テストが終わったら破棄する」という**完全に隔離されたクリーンな環境**を作るのが定石です。

しかし、Salesforceはマルチテナントクラウド上の**Sandbox組織**に依存するため、この定石が使えません。

- **環境のリセットが不可能**: Developer Sandboxはデータが空で、Full Sandboxのリフレッシュには数日かかります。テストのたびに環境を初期化することはできません。
- **並列実行によるデータ競合とレコードロック**: テストを高速化するためにPlaywright等で並列実行（Workers）を回すと、同じSandbox内の共有データや集計項目にアクセスが集中し、Salesforce特有の **`UNABLE_TO_LOCK_ROW`（レコードロックエラー）** でテストがランダムに失敗します。
- **ガバナー制限とテストデータの複雑さ**: API経由でテストデータを作ろうにも、複雑な入力規則、Apexトリガー、Flowが連鎖的に発火するため、データの前提条件を整えるだけで一苦労です。

---

## 根本原因④：MFA（多要素認証）強制化とセッション維持の壁

セキュリティ要件の厳格化により、Salesforce環境では**MFA（多要素認証）が必須**となっています。

CI/CDパイプライン上のヘッドレスブラウザからログインしようとすると、毎回認証コードやデバイス承認を求められるため、従来の「IDとパスワードを打ち込むだけ」のテストはログイン画面で即座に停止します。

かといって、メールの受信トレイをAPIで監視してOTPを抜き出すような実装にすると、メール着信の遅延でテストがタイムアウトしまくる泥沼にハマります（※この具体的な突破法については、[Salesforceテスト自動化で二段階認証を突破する現実解](/blog/salesforce-mfa-test-automation-bypass/) で詳しく解説しています）。

---

## 根本原因⑤：「年3回の強制アップデート」というリグレッションの主導権喪失

自社開発のWebシステムであれば、フロントエンドのフレームワーク（ReactやNext.js等）のバージョンを固定し、「テストがすべて通ることを確認してからバージョンを上げる」ことができます。**アップデートの主導権は開発チームにあります。**

しかし、Salesforceでは**年3回（Spring / Summer / Winter）のメジャーバージョンアップが強制適用**されます。

自社で1行もコードを修正していないにもかかわらず、ある朝突然Salesforce側の内部DOM構造やクラス名、非同期のタイミングがサイレントに変更され、**昨日までグリーンだった自動テストが一斉に赤（Fail）になる**という事態が定期的に発生します。

テストのメンテナンスコストを常に強制徴収され続けるため、「自動化で工数を削減するはずが、自動テストの保守で工数が溶ける」という本末転倒が起きやすいのです。

## 現場で爆死しないための「現実的な処方箋」

では、Salesforceプロジェクトでテスト自動化は諦めるべきなのでしょうか？  
結論から言うと、**「素のSeleniumやPlaywrightで、標準画面の端から端までE2Eテストを書こうとするアプローチ」は諦めるべき**です。

その上で、現場で生き残るための現実解は以下の4点に集約されます。

### ① テストピラミッドを極端に意識する（UIテストは最小限に）
Salesforce開発において最も費用対効果が高いのは、画面のE2Eテストではありません。
- **Apexテスト（単体テスト）**: ビジネスロジック、トリガー、Flowの検証はSalesforceネイティブのApexテストで徹底的に担保する（そもそも本番デプロイに75%以上のカバレッジが必須です）。
- **APIテスト**: 外部連携やデータ登録・更新のロジックはREST/Bulk API経由で直接検証する。
- **UI（E2E）テスト**: 最も壊れやすいため、**「画面でしか検証できない主要業務フロー（Critical Path）のスモークテスト」**のみに極限まで絞る。

### ② Salesforce公式「UTAM」の活用を検討する
Salesforce自身がこの問題を認識しており、公式に提供しているのが **UTAM（UI Test Automation Model）** です。
これはPage Objectパターンをベースに、Salesforce標準コンポーネントのセレクタ定義を公式がJSON形式で管理・配布してくれる仕組みです。バージョンアップで標準DOMが変わっても、UTAMのパッケージを更新することでセレクタの変更を吸収できます。

ただし、導入や設計の学習コストは相応に高いため、中〜大規模で長期運用するプロジェクト向けの選択肢です。

### ③ メタデータ認識型の商用テストツールを検討する
もし予算が確保できるなら、PlaywrightやSeleniumで自前実装に固執せず、Salesforceのアーキテクチャに特化した商用ツール（Provar、Tricentis、mabl等）を検討するのが最も合理的です。

特にSalesforceのメタデータを直接読み込んでテストを組み立てられるツールであれば、DOMの微妙な変化やShadow DOMの壁をツール側が吸収してくれるため、メンテナンス工数を劇的に減らせます。

### ④ テストデータの生成・認証をUIから切り離す
E2Eテストを実行する際、毎回画面からログインしてテストデータを作成していると、それだけでテストが重く不安定になります。
- **認証**: JWTベアラフロー等を使い、API経由でアクセストークンを取得してセッションを注入する（またはTOTPを動的に計算する）
- **データ準備**: テストの前提データはREST APIでテスト開始直前に作成し、UIテストは「そのレコードを開いてボタンを押すだけ」の状態に保つ

## まとめ

<ConclusionBox>
- **難しさの正体:** Shadow DOMや動的IDは表面現象に過ぎず、本質は「メタデータ駆動でDOMを所有できないこと」「Aura/LWC混在のSPA」「Sandboxの物理制約」「年3回の強制アプデ」という構造的要因にある
- **E2Eに頼りすぎない:** Apex単体テストとAPIテストでロジックの品質を固め、壊れやすいUIテストは重要フローのみに限定する
- **現実的な手段を選ぶ:** 自前スクラッチにこだわらず、UTAMの採用やメタデータ対応商用ツール、APIによるデータ・認証バイパスを組み合わせる
</ConclusionBox>

Salesforceのテスト自動化は、一般のWebアプリケーションと同じ感覚で突っ込むと高確率で火傷します。

しかし、「なぜ壊れるのか」というアーキテクチャレベルの根本原因を正しく理解していれば、**「ここはApexで守る」「ここはUTAMやAPIで逃がす」「UIテストはここだけに絞る」**という冷静な線引きができるようになります。まずは無理なカバレッジ100%を追いかけず、費用対効果の高いスモークテストから着実に構築してみてください。
