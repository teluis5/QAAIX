<ProblemBox>
- 「テスト環境に本番データをコピーするのは絶対NG」と分かっていても、現実のテストデータ準備で詰まっている
- 現行システムのUIやAPIでは作れない「特殊なレガシーユーザー（マイナンバー未登録など）」のテストをどうすればいいか悩んでいる
- 開発・QAチームが安全にテストを進められる、現実的なデータマスキングとテストデータ生成の設計指針を知りたい
</ProblemBox>

楽天証券をはじめ、金融機関や大手Webサービスにおいて「テスト環境（検証環境）に本番の顧客データを置いていたことによる情報漏洩・セキュリティインシデント」は、業界で定期的に発生する根深い問題です。

ニュースを見た一般の方からは「なぜわざわざ本番データをテスト環境に置くのか、信じられない」という声が上がります。しかし、**現場で日々テストを回しているテストエンジニア（QA）の目線で見ると、そこには「悪意ではなく、開発・テスト現場の構造的な事情と誘惑」が潜んでいる**ことが分かります。

本記事では、なぜテスト環境に本番データを置いてしまうのかという現場のリアルな理由と、テスト環境と本番環境の決定的な違い、そしてどうすれば防げたのか（現実的な対策）を解説します。

---

## なぜ現場はテスト環境に本番データを置いてしまうのか？

セキュリティガイドライン上、「テスト環境に本番の個人情報をそのまま持ち込まない」というのは基本中の基本です。それでもなお本番データのコピーが後を絶たないのには、大きく2つの現場事情があります。

### 1. テストアカウント・テストデータを一から作る圧倒的な手間
証券システムや銀行システムのような大規模な業務アプリケーションでは、1人のテストユーザーを作るだけでも膨大な前提条件が必要になります。

- 口座開設の申込、本人確認（eKYC）、審査完了ステータスの作成
- 連携銀行口座の登録、入出金履歴の生成
- 特定口座（源泉徴収あり/なし）、NISA口座、信用取引口座などの契約状態
- 実際に保有している株式・投資信託の銘柄と残高、過去の取引履歴・配当履歴

これらを画面やテストスクリプトから毎回一から組み立てるのは非常に手間がかかります。特に「リリース直前の障害再現テスト」や「バッチ処理の負荷テスト」では、**「本番と同じデータ量と複雑な絡み合いを持ったDBを今すぐ用意したい」というプレッシャーから、本番DBのダンプをそのままリストアする悪手に手を出しがち**です。

### 2. 「今のシステムでは作れないユーザー」の存在
テストエンジニアが最も頭を抱えるのが、**「現行のシステム仕様では新規作成できない、過去のレガシー状態のまま残っているユーザー」**の存在です。

たとえば、証券システムにおける代表例が**「マイナンバー未登録のユーザー」**です。

- 現在の新規口座開設フローではマイナンバー登録が必須化されているため、普通にテストアカウントを作ると全員「マイナンバー登録済み」になる
- しかし本番環境には、制度開始前から口座を持っていて「マイナンバー未登録のまま残っている既存顧客」が大量に存在する
- 法改正対応やUI改修のテストでは、「マイナンバー未登録のユーザーがログインしたときに正しく警告バナーが出るか」「特定の取引がブロックされるか」を必ず検証しなければならない

このような**「歴史的経緯でしか生まれないエッジケースのデータ」**を再現しようとすると、設計書やDBの関連テーブルをすべて解読してSQLで直接データを作るよりも、「本番から該当パターンのデータを引っ張ってくる」方が圧倒的に手っ取り早く見えてしまうのです。

## 本番環境とテスト環境の「決定的な違い」

「同じ社内の閉じた環境なのだから、本番データをテスト環境に置いても大差ないのでは？」という油断が命取りになります。本番環境とテスト環境では、セキュリティの前提が根本から異なります。

| 比較項目 | 本番環境 | テスト環境（検証・ステージング） |
| :--- | :--- | :--- |
| **アクセスできる人** | 限定された一部の運用担当者のみ | 開発者、QA、PM、外注（SES・オフショア）まで広範囲 |
| **物理的・環境的制限** | セキュアルーム（入退室管理・監視・私物持込禁止）等 | 通常の執務室やリモートワーク端末からアクセス可能 |
| **操作統制・監査** | 特権IDの事前申請・操作ログの常時監視・承認フロー | 開発効率優先でDB直接参照やログ出力が緩いことが多い |
| **ネットワーク境界** | 厳格なファイアウォールとアクセス制御 | テスト用に外部（テスト端末や検証用URL）から到達可能な場合がある |

つまり、**本番環境と同じレベルの厳重なガード（セキュアルームや厳格な権限分離）が敷かれていないテスト環境に本番データを置いた時点で、情報漏洩のリスクは桁違いに跳ね上がります。**

「テスト環境だから大丈夫」ではなく、「誰でも触れるテスト環境だからこそ、漏洩しても実害が出ないダミーデータしか置いてはいけない」のが鉄則です。

## どうすればよかったのか？テストエンジニア視点の4つの対策

では、レガシーデータの再現や複雑なテスト条件を満たしつつ、本番データの持ち込みをゼロにするにはどうすればよかったのでしょうか。現実的な解決策は以下の4点です。

### 1. 個人情報の徹底的なマスキング（仮名加工・匿名化）
どうしても本番データの構造や統計的偏りをベースにしたい場合でも、**テスト環境に流す前に必ず個人情報を不可逆変換（マスキング）するパイプライン**を通します。

- **氏名・住所・電話番号・メールアドレス・生年月日**: すべてランダムなダミー文字列（Faker等）や固定のテスト用フォーマットへ置換する。
- **復元不可能な設計**: ハッシュ化やランダム置換を行い、テスト環境のデータから元の個人を絶対に特定できない状態にする。

### 2. 口座番号や資産データのダミー変換（業務状態は保持する）
個人情報だけでなく、口座番号や保有資産額などの機微情報も変換が必要です。ここで重要なのは、**「テストに必要な業務ステータス（状態）だけは壊さずに残す」**という設計です。

- **口座番号**: 一意性を保ったまま別のダミー番号体系へ振り直す。
- **資産残高・取引金額**: 実際の金額はランダムな係数でスケーリング（または固定値へ丸め）する。ただし、「残高が0円かプラスか」「特定口座かNISAか」「マイナンバー未登録フラグが立っているか」といった**テストの分岐条件に関わるフラグ・状態値だけは維持**する。

これにより、実在の顧客資産を一切露出させることなく、「マイナンバー未登録で、かつNISA口座を持ち、残高がプラスのユーザー」というテストケースを安全に検証できます。

### 3. 本番環境とは独立した「テストデータ生成基盤」の開発
最も本質的な解決策は、**本番データに一切依存せず、テスト環境内で任意のユーザー状態を自動生成できる仕組み（Seed / Factory / 管理ツール）を作ること**です。

「今のシステムでは作れないマイナンバー未登録ユーザー」であっても、開発チームが少し手間をかけて以下のような追加開発を行えば再現可能です。

- テスト環境専用の「テストユーザー生成API / バッチ」を用意し、引数で `myNumberRegistered: false` や `accountType: 'LEGACY'` を渡せるようにする
- 既存のテストアカウントのDBステータスをワンクリックで書き換える「QA用デバッグ管理画面（テスト環境限定で有効化）」を実装する

確かに初期の追加開発コストはかかります。しかし、一度本番データのコピーに頼り始めると、**「テストデータを作る仕組み」への投資が一生後回しになるという技術的負債**に陥ります。

### 4. ネットワーク分離とテスト環境のアクセス制御の徹底
仮にマスキング済みデータや合成データであっても、テスト環境がインターネットから無防備にアクセスできる状態は危険です。

- テスト環境へのアクセスはVPN・IP制限・SSO認証を必須にする
- CI/CDパイプラインから本番DBへの接続権限を物理的に遮断し、誤って本番データをテスト環境へエクスポートできないインフラ構成（IAM権限分離）にする

## まとめ

<ConclusionBox>
- **本番データ流用の背景:** 複雑なアカウント作成の手間や、「マイナンバー未登録」など現行システムで作れないレガシー状態の再現ニーズが現場の誘惑を生む
- **環境の境界を意識する:** 開発者や外注先など多くの人が触れ、セキュアルーム等の物理制限がないテスト環境に本番の生データを置くこと自体が構造的なリスク
- **本質的な対策:** 個人情報の不可逆マスキングと口座・資産のダミー変換（状態フラグのみ保持）を徹底し、中長期的には独立したテストデータ生成基盤への追加開発投資を行う
</ConclusionBox>

「テストデータを作るのが面倒だから本番からコピーする」という選択は、短期的にはテスト工数を削減できたように見えます。しかし、一度インシデントが起きれば企業の信頼と莫大な対応コストを失うことになります。

QAエンジニアや開発チームは、「どうやって本番データを使わずに複雑なテスト状態を再現するか」という**テスト容易性（Testability）の設計**を、開発初期の要件として堂々と要求し、仕組み化していくことが求められます。
