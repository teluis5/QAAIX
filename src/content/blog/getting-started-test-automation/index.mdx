<ProblemBox>
- 「sleep禁止」「data-testid採用」などの基本は守っているのに、テストが不安定でメンテナンス地獄から抜け出せない
- 並列実行するとテスト同士がデータを奪い合ってランダムに失敗する（Flaky Tests）
- 毎朝CIが赤くなり、誰もテスト結果を信用せず「とりあえずRe-run（再実行）」するのが習慣化している
</ProblemBox>

## なぜ「教科書通りのベストプラクティス」だけでは失敗するのか

「リリース前の手動リグレッションをなくそう」と始まったテスト自動化プロジェクトが、半年後には**「誰もメンテできず、CIが落ちても再実行ボタンでやり過ごすだけの巨大な負債」**に成り果てる——これは多くの開発現場で繰り返されている現実です。

世の中の入門記事では「テストピラミッドを守ろう」「`sleep`を禁止しよう」「`data-testid`を使おう」と説かれます。もちろんこれらは正しいのですが、**実際の現場でテストが崩壊する原因はもっと構造的な部分にあります。**

本記事では、テスト自動化が負債化する本質的なメカニズムと、現場で本当に機能するテストスイートを構築・運用するための実践的な設計原則を解説します。

---

## テスト自動化が負債化する3つの構造的要因

### 1. テストデータの「相互汚染」と状態の共有
ローカルで1本ずつ動かすと100%通るのに、CIで並列実行した瞬間にランダムで落ちる。この最大の原因は**「テスト間の状態共有（State Pollution）」**です。

- テストAが「テストユーザー1」のプロフィールを更新している最中に、テストBが同じ「テストユーザー1」を削除・変更してしまう
- 前回のテスト失敗でゴミデータ（作成途中のレコード）がDBに残り、次のテストの検索結果件数アサーションがズレる
- 画面から毎回ユーザー登録とログインを繰り返すため、1テストあたりの実行時間が肥大化し、タイムアウトが頻発する

### 2. 「モックの過剰適用」によるテストの形骸化
テストを高速化・安定化させようとしてAPIや外部連携をすべてモック（Stub）に置き換えた結果、**「テストは毎回オールグリーンなのに、本番環境で盛大にバグる」**という本末転倒が起きます。

モックは「仕様変更（APIレスポンスの型変更やエラーコードの追加）」を検知できません。結合ポイントの検証をすべてモックで逃げてしまうと、自動テストは「自分たちが書いたモックの仕様」をテストしているだけの空虚な存在になります。

### 3. 「壊れた窓」を放置する運用設計の欠如
人間は「たまに落ちるテスト（Flaky Test）」が2〜3本混ざるだけで、急速にテストスイート全体への信頼を失います。

「また例のテストがタイミング悪く落ちただけだろう」と全員がスルーし始めると、**本物のバグ（デグレ）が起きても誰も気づかなくなります。** テストが落ちたときに「直すか、即座に隔離（Quarantine）するか」のルールがない組織では、自動化は確実に破綻します。

## 現場で生き残るための実践的アプローチ

### 原則1：テストデータの完全隔離（Test Isolation）と認証バイパス
E2Eテストにおいて最も重要なのは、**「どのテストをどの順番で・何並列で動かしても絶対に干渉しない」**設計にすることです。

- **テストごとに独立したデータを生成する**: 共有の固定ユーザー（`test@example.com`等）を使い回すのをやめ、テストの事前準備（Setup）でAPI経由でユニークなユーザーやデータを動的生成し、テスト終了後に破棄します。
- **認証フローは `storageState` で使い回す**: 毎テストでログイン画面を操作するのは時間と不安定さの無駄です。Playwrightの `storageState` のように、ログイン後のCookieやLocalStorageを保存して全テストに注入する仕組みを使い、テスト本体の開始地点を「ログイン済み状態」にショートカットします。

```typescript
// Playwrightの例：認証状態を1回だけ作成して全テストで共有する
import { test as setup } from '@playwright/test';

setup('authenticate', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill(process.env.TEST_USER!);
  await page.getByLabel('Password').fill(process.env.TEST_PASS!);
  await page.getByRole('button', { name: 'ログイン' }).click();
  await page.waitForURL('/dashboard');

  // 認証状態をJSONに保存し、後続テストで使い回す
  await page.context().storageState({ path: 'playwright/.auth/user.json' });
});
```

### 原則2：テストピラミッドを「リスクとコスト」で再定義する
E2Eテストは維持コストが最も高いため、何でもかんでもブラウザで検証してはいけません。

```
        ▲
       / \      E2E Tests (最上層: 業務の生命線のみ)
      /   \     - 決済、認証、主要コンバージョンのハッピーパス
     /-----\
    /       \   API / Integration Tests (中層: 仕様変更の検知)
   /         \  - モックなしのDB結合、APIスキーマ・権限チェック
  /-----------\
 /             \ Unit Tests (基底層: ロジックの網羅)
/---------------\ - 境界値、バリデーション、複雑な状態遷移
```

- **バリデーションやエラーパターンはUnit/APIテストへ逃がす**: 「パスワードが8文字未満のときのエラーメッセージ」をわざわざブラウザを立ち上げて検証する必要はありません。
- **外部API以外は極力モックしない**: バックエンドとの結合テストやE2Eテストでは、自社のAPIとDBは実際に繋いで動かし、決済代行やメール送信など「外部の制御不能なシステム」だけをモックまたはサンドボックス環境に向けるのが鉄則です。

### 原則3：Flakyテストを「仕様として許容しない」運用ルール
「たまに落ちるテスト」を放置するとプロジェクト全体が腐敗します。ツール側の機能と運用ルールを組み合わせて、信頼性を死守します。

1. **リトライ回数の適切な設定とトレース記録**: CI上では `retries: 2` のように自動リトライを設定しつつ、失敗時のみTrace（動画・ネットワークログ・DOMスナップショット）を保存して原因調査コストを下げます。
2. **「リトライで通ったテスト（Flaky）」の可視化と隔離**: リトライで救済されたテストは「潜在的なバグまたはテスト設計ミス」です。放置せず専用タグで隔離（またはチケット化）し、原因が解消されるまでPRのマージブロッカーから外す判断も必要です。
3. **CIのShard分割による高速フィードバック**: E2Eテストが10分を超えると開発者は待てなくなります。GitHub ActionsのMatrix機能とPlaywrightの `--shard=1/4` などを組み合わせ、数分で結果が返るパイプラインを維持します。

## まとめ

<ConclusionBox>
- **負債化の正体は「状態共有」と「運用の崩壊」:** `sleep`禁止だけでなく、テストデータの相互汚染を防ぐ独立設計が不可欠
- **認証とデータ準備はUIから切り離す:** `storageState` やAPI経由のデータセットアップで、テストを高速・安定化させる
- **Flakyテストを放置しない:** 自動リトライ＋Trace記録で原因を特定し、信頼できないテストは即座に隔離してCIの信用を守る
</ConclusionBox>

テスト自動化は「一度書いたら終わりの魔法」ではなく、プロダクトコードと同じように**設計・リファクタリング・運用設計**が求められるエンジニアリングそのものです。まずは今あるテストの中から「最もよく落ちる不安定なテスト」を1本選び、データの独立性と待機処理を見直すところから始めてみてください。
