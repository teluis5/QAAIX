<ProblemBox>
- 複数台のiPhoneをmacOSに接続して自動テストを並列実行したいが、接続が頻繁に切れる
- デバイスハブ（USBハブ）経由でiOS実機を繋ぐと、充電されなかったり認識が不安定になったりする
- AppiumやXCUITest（WebDriverAgent）を複数端末で同時に動かす際のポート競合や署名・運用設計を知りたい
</ProblemBox>

## なぜ「macOS × デバイスハブ」構成が必要になるのか

iOSアプリのテスト自動化では、シミュレータ（Xcode Simulator）である程度の検証は可能です。しかし、**プッシュ通知、カメラ/生体認証、バックグラウンド復帰、特定OSバージョン・実機特有のメモリ制約や描画バグ**を検証するには、実機テストが不可欠です。

クラウドのデバイスファーム（AWS Device FarmやBrowserStack等）は手軽ですが、**社内クローズド環境への接続要件、テスト実行コストの増大、常時稼働の自動運用**が求められる現場では、Mac miniなどに産業用USBデバイスハブを接続して**オンプレミスのiOSテスト基盤**を構築するケースが多くあります。

本記事では、macOSホストにデバイスハブを接続して複数台のiOS実機を安定稼働させるための**ハードウェア選定からソフトウェア設計までの実践ノウハウ**を解説します。

## 物理レイヤーの壁：USBデバイスハブ選定と接続の鉄則

iOS実機の複数台接続で最も多いトラブルは、コードやAppiumの設定ではなく**「USBの電源と帯域不足」**です。

### 1. バスパワーは厳禁！必ず「セルフパワー（AC電源付き）」を選ぶ
iPhoneはテスト実行中（画面常時点灯・CPUフル稼働・通信発生）に大きな電力を消費します。PCのUSBポートから給電するバスパワーハブでは電力が足りず、**「テスト中にバッテリーが減り続けてシャットダウンする」「一瞬だけUSB接続が切れて `usbmuxd` がセッションを失う」**という現象が必ず起きます。

- 各ポートあたり **最低1.5A〜2.4A** を安定供給できる産業用・業務用のセルフパワーUSBハブ（CambrionixやAnker等の高出力モデル、または管理機能付きスマートハブ）を選定してください。
- ポート単位で電源のON/OFF（USBポートリセット）をCLIやAPIから制御できるスマートハブを使うと、端末フリーズ時の自動復旧が劇的に楽になります。

### 2. ハブの「多段接続（デイジーチェーン）」を避ける
MacのUSB-C/Thunderboltポートの帯域を1つのハブに集中させたり、ハブにハブを繋いだりすると、アプリ（`.ipa`）のインストール転送時やスクリーンショット・動画キャプチャの通信でUSBコントローラが飽和します。

Mac miniであれば背面の独立したポートへ分散接続し、1ハブあたりの同時接続台数は**4〜8台程度**に抑えるのが安定稼働の目安です。

## ソフトウェア設計：複数台を並列制御するアーキテクチャ

物理的に接続できたら、次はmacOS上で複数台のiOS端末を競合なく制御する仕組みを作ります。

```
[CI/CD (GitHub Actions / Jenkins)]
       │
       ▼
[macOS Host (Mac mini)]
  ├── Appium Server (Port 4723) ──▶ WDA (wdaLocalPort: 8101) ──▶ iPhone A (UDID-1)
  ├── Appium Server (Port 4725) ──▶ WDA (wdaLocalPort: 8102) ──▶ iPhone B (UDID-2)
  └── usbmuxd / pymobiledevice3 (USB通信・トンネル管理)
```

### 1. UDIDの特定とポート番号の完全分離
複数台を同時に動かす際、**WebDriverAgent（WDA）のローカルポートがデフォルト（`8100`）のままだと、2台目以降の起動でポート競合を起こして失敗**します。

接続されている端末のUDIDを検出し、端末ごとに専用のポートを割り当てます。

```bash
# 接続中のiOS実機のUDID一覧を取得
xcrun xctrace list devices
# または libimobiledevice を利用
idevice_id -l
```

AppiumのCapabilitiesでは、端末ごとに以下のように `udid` と `wdaLocalPort` を明示的に分離して渡します。

```json
{
  "platformName": "iOS",
  "appium:automationName": "XCUITest",
  "appium:udid": "00008110-001234567890001E",
  "appium:wdaLocalPort": 8101,
  "appium:derivedDataPath": "/tmp/wda-device-1"
}
```

> **重要ポイント:** `derivedDataPath` も端末（またはプロセス）ごとに分けておくと、並列ビルド時のファイルロック競合を防げます。

### 2. WDAの事前ビルド（`xcodebuild`）でテスト起動を高速化
毎回テスト開始時にWDAをコンパイルしていると、それだけで数十秒〜数分を消費します。CIのジョブ実行前に `xcodebuild build-for-testing` でWDAをビルド済みの状態にしておき、テスト実行時は `usePrebuiltWDA: true` を指定するのが定石です。

## 長期運用で必ず直面する3つのトラブルと対策

### 1. `usbmuxd` のハングと認識ロスト
macOSでUSB接続を管理するデーモン `usbmuxd` は、長期間デバイスを繋ぎっぱなしにすると稀にハングし、すべての端末が認識できなくなることがあります。

- **対策**: 定期メンテナンススクリプトで異常検知時に `sudo killall -STOP -c usbmuxd` 等で再起動するか、スマートUSBハブのポート電源をCLIでリセットする仕組みを組み込みます。
- また、iOS 17以降のDeveloper Disk Imageマウントやトンネル通信には、`xcrun devicectl` や `pymobiledevice3` などの最新ツールチェーンを組み合わせて自動化します。

### 2. 「このコンピュータを信頼しますか？」ダイアログ
OSアップデートや再起動後、ロック解除と「信頼（Trust）」の承認を求められることがあります。テスト基盤の端末は **パスコードをオフ（または自動入力可能な構成）** にし、一度信頼済みにしておけば日常的な再承認は防げますが、メジャーOSアップデート時は手動確認が必要です。

### 3. バッテリーの過充電・膨張と熱暴走
24時間365日USBハブに繋ぎっぱなしにしていると、iPhoneのバッテリーが劣化して膨張（画面が浮き上がる）するリスクがあります。

- **対策**:
  1. 電源制御付きスマートハブを使い、**テストを実行していない夜間や待機中はUSB給電をOFF**にする（またはバッテリー残量80%前後で給電を止める運用）。
  2. アルミ製の放熱ラックや冷却ファンを設置し、複数台の端末が密着して熱がこもらないように物理配置を工夫する。

## まとめ

<ConclusionBox>
- **ハードウェアが9割:** バスパワーは厳禁。高出力なセルフパワーUSBハブ（できればポート単位の電源制御付き）を選定する
- **ポートとパスの分離:** 並列実行時は端末ごとに `udid`・`wdaLocalPort`・`derivedDataPath` を完全に分離する
- **長期運用の仕組み化:** `usbmuxd` のリセット手段と、待機中の給電制御（バッテリー膨張対策）を最初から設計に組み込む
</ConclusionBox>

macOSとデバイスハブを組み合わせたiOS実機テスト基盤は、一度安定稼働する仕組みを作ってしまえば、クラウド課金を抑えつつ社内ネットワーク内のアプリも高速にテストできる強力な武器になります。まずは2〜4台の小規模構成から電源とポート分離を検証し、段階的にスケールさせてみてください。
